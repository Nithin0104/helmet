# Home Page — Principal PM Review

*Lens: product value, user flows, feature honesty, expectation-setting.*
See [`README.md`](./README.md) for the priority matrix. Related engineering detail in
[`03-frontend.md`](./03-frontend.md).

## Executive read

The home page tells a coherent story — offer hero → trust stats → brand proof → shop the
range → helmets & accessories → why us → compare → showroom → social proof. The
**information architecture is sound** and the content is fully data-driven, which is
exactly right for a storefront that will later be CMS/API-fed.

The product risks are not about *what* is on the page but about **affordances that promise
more than the app delivers**: buttons that go nowhere meaningful, a wishlist with no
wishlist, a quick-add that under-specifies the order, and a compare tool that doesn't
exist. Each one quietly erodes trust — the most expensive thing to lose on a commerce
home page.

---

## P1 · High · M — Dead / misleading navigation (everything routes to `/shop`)

**Problem.** Almost every interactive destination on the page points at `/shop`, and two
of them are actively misleading. A rider who taps **"Get directions"** expects a map;
**"Store hours"** expects hours — both dump them on the product listing. Category cards
that say "Helmets / Spares / Accessories / Care" all land on the same unfiltered `/shop`,
so the taxonomy is decorative.

**Evidence.**
- `src/data/home.ts:53-58` — all four `CATEGORIES` use `href: '/shop'`.
- `src/data/home.ts:105-106` — showroom `primary` "Get directions" and `secondary`
  "Store hours" both `href: '/shop'`.
- `src/data/home.ts:84` — compare `link` "Start comparing →" → `/shop`.
- `src/data/home.ts:29-30` — hero "Shop offers" → `/shop`, "New in" → `/shop`.
- DC parity: DC's "New in" is an **in-page anchor** (`href="#new"`) to the helmets rail,
  and its category/showroom links are placeholder `#` — so DC never claimed these worked
  either, but our real router makes the dead-end visible.

**Solution (per destination).**
- **Category cards** → deep-link to a filtered PLP, e.g. `/shop?category=Full-face`. Blocked
  on the PLP reading query params; until then, keep `/shop` but track this as the intended
  target so the taxonomy becomes real.
- **Showroom "Get directions"** → external map URL (or a `/showroom` page). **"Store hours"**
  → a small hours modal/disclosure, or fold hours into the panel and drop the button.
- **Compare "Start comparing"** → see P5; disable or defer until the compare tool exists.
- **Hero "New in"** → the new-arrivals rail (in-page anchor, matching DC intent) or
  `/shop?sort=new`.

**Verify.** Every CTA lands somewhere whose content matches its label; no button's promise
outruns the app. Add the nav targets to the routing integration test once wired.

## P2 · Med · S — Wishlist heart implies a feature that doesn't exist

**Problem.** Every product tile in both home rails shows a save/wishlist heart. There is
no wishlist feature, and the button does nothing when clicked — a false affordance on the
highest-traffic page.

**Evidence.** `src/components/composite/ProductCard/ProductCard.tsx:65-69` — heart button
has `aria-label="Save …"` but **no `onClick`**. Enabled on home via
`src/components/composite/ProductRail/ProductRail.tsx:115` (`heart`). (Full engineering
detail in **F3**.)

**Solution.** Either build a minimal wishlist (localStorage-backed, mirroring the cart
pattern) or remove `heart` from the home rails until it exists. Removing it also matches
the DC home, which did not enable the heart. Recommended: **remove now, build later** —
don't ship a control that lies.

**Verify.** No non-functional affordance on rail cards; if built, saved items persist and
surface somewhere the user can find them.

## P3 · Med · M — Quick-add is a poor commerce flow for variant products

**Problem.** The rail "＋ Quick add" adds a helmet to the cart **without a size or colour**.
Helmets are variant products (the PDP *requires* size + colour). A cart line with no
variant is either an incomplete order or a support ticket, and it can create duplicate
lines that don't merge with the properly-specified PDP line.

**Evidence.** `ProductCard.tsx:42-46, 77-81` — `handleAdd` calls
`add({ productId, name, brand, price })` with no colour/size; enabled on home via
`ProductRail.tsx:115` (`quickAdd`). (Cart-shape detail in **F4**.) DC home did not enable
quick-add.

**Solution (decide — ❓ product call).**
- **Recommended:** rail cards route to the PDP for variant selection; reserve one-tap
  quick-add for **variant-less accessories** only (gloves-in-one-size, care kits).
- Or: quick-add opens a lightweight size/colour mini-picker (bottom sheet) before adding.
- Or: quick-add with an explicit, labelled default variant ("adds size M / Matte Black").

**Verify.** Cart lines originating from the home carry the same shape as PDP lines, or
quick-add is scoped to items that genuinely have no variant.

## P4 · Low · S — Trust inconsistency: 4.9 headline vs 5-star cards

**Problem.** The reviews header advertises **★ 4.9 / 2.1k**, but every review card in the
marquee shows a **full 5 stars**. A skeptical shopper notices, and it reads as inflated.

**Evidence.** Header `src/data/home.ts:139` (`STORE_RATING`) and
`src/pages/HomePage/sections/ReviewsMarquee.tsx:22`; cards hardcode `rating: 5` at
`ReviewsMarquee.tsx:11-13`. (Fix in **F1**.)

**Solution.** Give each `HOME_REVIEWS` entry a real rating (a spread that averages near
4.9) and render it. Small change, real credibility gain.

**Verify.** Card ratings vary and are consistent with the advertised average.

---

## P5 · Low · S — Compare CTA promises a tool that isn't built

**Problem.** A prominent band invites the user to "Weigh up to 3 helmets side by side" with
a "Start comparing →" CTA. The comparison feature does not exist (documented as deferred in
`docs/phase-3-home.md §10`), but nothing on the page signals that — it reads as live.

**Evidence.** `src/data/home.ts:80-85`; `src/pages/HomePage/sections/CompareBand.tsx`.

**Solution.** Manage the expectation: label it "Coming soon", visually soften the CTA to a
non-actionable state, or defer the band's visibility until the tool ships. Keep the band if
it's useful as a roadmap signal — just don't present a live affordance.

**Verify.** The CTA's state honestly reflects whether the feature works.

---

## P6 · info — The content model is a clean CMS seam (protect it)

**Observation.** All home copy, stats, categories, why-us, showroom and reviews live in
`src/data/home.ts` behind typed interfaces — the presentational/data split the project
wants, and the exact seam a backend/CMS fills later. This is a genuine strength.

**Recommendation.** Guard it with a contract test (see **Q2**) so a future content edit
(or an API swap) can't silently ship a broken shape — the same protection `products.ts`,
`accessories.ts` and `navigation.ts` already have.
